# 신시(神屍) — 프로젝트 원페이저

> 상태: 초안 v0.2 / 기술 검증 전
> 이 문서는 수직 슬라이스 통과 전까지 확정 문서가 아니다. 모든 수치는 검증용 가정치다.
> 관련 문서: `01-design-bible.md` (세계관·직업·시스템 상세), `02-art-guide.md` (아트 방향)

## 1. 한 줄

**찢긴 전쟁신의 몸 위에 세운 도시에서, 번지는 저주를 막으며 버티는 액션 RPG.**

## 2. 로그라인

전쟁의 신 치우는 안개 너머의 세력에 패해 몸이 찢겼고, 승자는 그를 묶었던 족쇄에 저주를 걸었다. 사람들은 흩어진 그의 몸 위에 도시 신시를 세우고, 몸에서 신수(神髓)를 캐내 문명을 일으켰다. 저주는 지금도 치우의 몸을 갉아먹는다. 저주가 닿은 구역은 기하와 생태가 뒤틀려 더 이상 사람이 살 수 없는 곳이 된다. 플레이어는 무당으로서 신수를 회수해 구역의 저주를 늦추고, 이미 삼켜진 구역 깊숙이 내려가 더 많은 신수를 긁어온다.

## 3. 핵심 훅

**맵이 저주에 잠식된다. 저주는 멈추지 않는다.**

- 플레이어는 저주를 **막을 수 없다**. 오직 **늦추고, 어디를 포기할지 고를** 뿐이다.
- 포기한 구역은 사라지지 않는다. **영구 변형되어 고난도·고보상 던전이 된다.**
- 즉, 실패가 콘텐츠가 된다. 이것이 장르 내 유일한 차별점이자 전 개발 리스크의 근원이다.

## 4. 장르 / 레퍼런스

- 장르: 아이소메트릭 핵앤슬래시 ARPG (디아블로 계열)
- 전투·루팅·빌드: Diablo 4, Last Epoch, Grim Dawn
- 거점 운영·자원 압박: Darkest Dungeon, Frostpunk
- 영구 변형 월드: Hades(구조 아님, 반복 정당화 방식만), Dead Cells(레벨 조립 방식)

## 5. 플랫폼 / 규모

- 1차: PC (Steam)
- 2차 검토: 콘솔 (Xbox/PS)
- 상업용 본격 규모. 단, **수직 슬라이스 통과 전까지 본 개발 인력 투입 금지.**

## 6. 코어 루프

```
[도시] 정화 의식 → 어느 구역을 지킬지 결정 (신수 배분)
   ↓
[강하] 저주 구역으로 진입 → 전투 / 루팅 / 신수 회수
   ↓
[귀환] 신수·장비 반입 → 빌드 강화
   ↓
[시간 경과] 모든 구역 저주 수치 상승 → 일부 구역 전화(轉化)
   ↓
[도시] 줄어든 선택지로 다시 결정
```

핵심: **신수는 항상 모자라게 설계한다.** 전 구역 유지는 수학적으로 불가능해야 한다. 플레이어의 모든 세션은 "무엇을 버릴 것인가"로 끝나야 한다.

## 7. 저주 시스템 — 1차 가정치

> 아래 수치는 **본 게임의 다구역 배분 모델**(사이클 = 강하 1회, 구역별 이산적 진행)에 대한 1차 가정값이다. 맛보기 프로토타입 v4는 구역 1개·실시간 초 단위 모델을 쓰며, 그 실제 값은 `01-design-bible.md` 5장에 있다. 두 모델은 다구역 시스템 설계 시 하나로 합친다.

| 항목 | 가정값 | 비고 |
|---|---|---|
| 저주 수치 범위 | 0 ~ 100 (구역별) | |
| 자연 상승 | 사이클당 +8 | 사이클 = 강하 1회 |
| 정화 1회 효과 | -25 | 신수 소모 |
| 사이클당 획득 신수 | 정화 1.5회분 | 구역 수보다 항상 적게 |
| 전화 임계 | 100 도달 시 즉시 | **되돌릴 수 없음** |

### 저주 단계 (시각·게임플레이 동시 변화)

1. **평온 (0-25)** — 기본 지형, 기본 적 테이블
2. **징후 (26-50)** — 텍스처 변색, 적 밀도 +20%, 엘리트 출현
3. **침식 (51-85)** — 지형 일부 붕괴(통로 폐쇄/개방), 변이 적 등장, 드랍 등급 +1
4. **전화 (86-100 → 100)** — **구역 영구 교체.** 레이아웃·적·보스·드랍 테이블 전면 변경. 도시 기능 1개 영구 상실.

> 위 4단계는 요약이다. `01-design-bible.md` 5.2는 "전화 임박(86-99)"과 "저주에 삼켜짐(100)"을 나눠 5단계로 구분한다 — 프로토타입에서 전화 직전 연출(화면 어두워짐, 장단 최고속)을 별도로 넣었기 때문. 다구역 설계 시 이 5단계 구분을 기준으로 삼는다.

> 설계 원칙: 전화는 **벌이자 보상**이어야 한다. 순수한 벌이면 플레이어는 세이브 스컴을 하고, 순수한 보상이면 정화 시스템 자체가 죽는다. 이 균형이 본 프로젝트의 최대 난제다.

## 8. 기술 리스크 명세 (검증 대상)

수직 슬라이스는 재미를 검증하는 게 아니라 **아래 5개가 구현 가능한지**를 검증한다.

> **현재 상태 (2026-09-21): R1~R5 전부 미검증.** 맛보기 프로토타입 v4는 구역이 1개뿐이라 다구역 전제인 이 리스크들을 아직 건드리지 못했다. v4는 "전투·성장·루팅이 재밌는가"만 검증했다. 9장의 수직 슬라이스 범위(구역 2~3개 + 전화 1회 영속)를 다음 프로토타입으로 잡아야 R1~R5를 실제로 검증할 수 있다.

### R1. 런타임 구역 재구성
- 문제: 전화 시 지형 메시, 콜리전, 네비게이션, 라이트맵을 런타임에 교체해야 함
- 검증: 전환 시 프레임 히치가 허용 범위 내인가? 로딩 화면으로 가릴 것인가?
- 실패 시: 전화를 "구역 재진입 시 적용"으로 후퇴 (몰입 손실 감수)

### R2. 세이브 데이터 영속화
- 문제: 구역 N개 × 상태(저주 수치, 전화 여부, 변형 이력, 파괴된 오브젝트) 전부 저장
- 검증: 세이브 파일 크기와 로드 시간이 선형으로 폭증하지 않는가?
- 설계 방향: 전체 상태 저장 금지. **시드 + 차분(delta)만 저장**

### R3. 동적 스폰 / 드랍 테이블
- 문제: 저주 단계별로 적·드랍이 전면 교체됨
- 검증: 테이블이 코드가 아닌 **데이터(JSON)로 완전히 분리**되는가?
- 원칙: 밸런싱을 코드 수정으로 하게 되면 그 시점에 프로젝트는 실패다

### R4. 저주 가독성 (UX)
- 문제: 플레이어가 저주 진행을 **예측 가능**해야 한다. 안 그러면 불공정하게 느껴짐
- 검증: 신규 플레이어가 튜토리얼 없이 "이 구역은 곧 넘어간다"를 인지하는가?
- 수단: 지형 시각 변화 + 도시 UI 게이지 + 사운드 큐, 3중 전달

### R5. 전화의 보상 균형
- 문제: 7번 설계 원칙 참조
- 검증: 테스터가 전화를 "당했다"고 느끼는가, "각오한 거래"로 느끼는가?
- 이건 코드가 아니라 플레이테스트로만 검증됨

## 9. 수직 슬라이스 범위

### 포함
- 구역 **1개**, 저주 단계 **4단계 전부**, 전화 **1회**
- 적 **2종** (기본 1 + 변이 1)
- 플레이어 스킬 **1개** + 기본 공격
- 도시 화면: 신수 배분 UI만 (텍스트 UI 가능)
- 그래픽: **전부 도형/프리미티브.** 아트 에셋 제작 금지

### 제외 (하지 말 것)
- 아이템 시스템, 빌드, 스킬트리
- 스토리, 대사, 컷신, NPC
- 사운드, 이펙트, 최종 아트
- 구역 2개 이상
- 멀티플레이 고려

> 슬라이스에서 아트를 만들기 시작하면 검증이 아니라 개발이 된다. 도형으로 재미없으면 아트를 입혀도 재미없다.

> 참고: 맛보기 프로토타입 v4는 이 슬라이스 범위를 넘어 이미 아이템 시스템·사운드·스토리 도입부·완성된 비주얼까지 구현했다 (구역 1개 안에서). **다음 슬라이스는 정확히 이 장이 원래 정의한 범위 — "구역 2~3개 + 전화 1회 영속" — 로 좁혀서, R1~R5를 검증하는 데만 집중해야 한다.**

## 10. Go / No-Go 판정 기준

| 기준 | 통과 조건 |
|---|---|
| R1 | 전화 전환이 5초 이내 로딩 또는 무중단으로 처리됨 |
| R2 | 구역 100개 가정 시 세이브 파일 5MB 이하 추정 |
| R3 | 적 테이블을 코드 빌드 없이 JSON 수정만으로 교체 가능 |
| R4 | 테스터 5명 중 4명이 전화 발생을 사전에 인지 |
| R5 | 테스터 다수가 전화 직후 "계속하고 싶다"고 응답 |

**하나라도 실패 시 세계관 바이블 착수 금지.** 훅을 수정하거나 프로젝트를 접는다.

> 이 기준은 이미 `01-design-bible.md`가 존재하는 지금도 유효하다 — 세계관 바이블은 "착수"했지만(내용을 다 채웠지만), 이 표의 검증은 아직 안 끝났다. 다구역 슬라이스로 R1~R5를 통과시키기 전까지 본 게임 개발 착수는 보류 상태로 본다.
